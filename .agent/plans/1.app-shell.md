# Plan 1: App Shell + Observability (Module 1)

⚠️ **Medium**: Single-pass is realistic if the prerequisites below are in place first, but the plan covers three surfaces at once (Supabase, FastAPI, React), and streaming Responses API events over SSE usually takes some iteration. Each phase ends at a working checkpoint. If a pass stalls, run the phases as separate sub-plans (1a Foundation, 1b Backend, 1c Frontend).

## Goal

A logged-in user can create chat threads, send messages, and get streamed answers from the OpenAI **Responses API**. OpenAI manages the conversation memory and runs `file_search` over a vector store. Each LLM call is traced in LangSmith.

## Out of Scope (Module 2+)

- Ingestion UI, file upload, chunking, embeddings, pgvector
- Chat Completions API, OpenRouter, self-managed history sent to the model
- Realtime ingestion status

## Prerequisites (the user must provide these before building)

| Item | Where to get it |
|------|-----------------|
| Supabase project URL + anon (or publishable) key | Supabase dashboard → Project Settings → API |
| OpenAI API key | platform.openai.com → API keys |
| OpenAI vector store ID (`vs_...`) with a few test documents | platform.openai.com → Storage → Vector stores: create one and upload 1–3 files |
| LangSmith API key | smith.langchain.com → Settings → API Keys |
| Email auth enabled in Supabase; for local dev, turn **off** "Confirm email" | Supabase → Authentication → Providers / Sign In settings |

The agent must never read `.env` files (blocked by `.claude/settings.json`). It writes `.env.example` files, and the user copies them to `.env` and fills in the values.

## Key Decisions

1. **Thread memory = OpenAI Conversations.** Each app thread stores an `openai_conversation_id`. Every message calls `client.responses.create(conversation=<id>, input=<user text>, ...)`, so OpenAI keeps the context. We don't send history ourselves; that starts in Module 2.
2. **Messages are also saved in Supabase, for display only.** The UI reloads thread history from our `messages` table instead of calling OpenAI. Saved messages are **not** sent to the model in Module 1. This keeps the UI fast and makes the Module 2 switch easier.
3. **Backend enforces RLS with the user's token.** For each request, FastAPI checks the Supabase JWT with `supabase.auth.get_user(token)` and builds a Supabase client that carries that token. Postgres RLS then applies to every query. No service-role key in Module 1.
4. **Frontend talks to Supabase only for auth.** All thread and message data goes through FastAPI.
5. **SSE via `fetch` + `ReadableStream`.** We don't use `EventSource`, because it can't send a POST body or an `Authorization` header.
6. **The vector store is fixed by an env var** (`OPENAI_VECTOR_STORE_ID`). The user manages files in the OpenAI dashboard. There's no upload UI in Module 1.

### Task A2: Database schema + RLS

Create `supabase/migrations/001_threads_messages.sql`:

```sql
create table public.threads (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
  title text not null default 'New chat',
  openai_conversation_id text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table public.messages (
  id uuid primary key default gen_random_uuid(),
  thread_id uuid not null references public.threads(id) on delete cascade,
  user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
  role text not null check (role in ('user', 'assistant')),
  content text not null,
  created_at timestamptz not null default now()
);

create index on public.threads (user_id, updated_at desc);
create index on public.messages (thread_id, created_at);

alter table public.threads enable row level security;
alter table public.messages enable row level security;

create policy "own threads" on public.threads
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);

create policy "own messages" on public.messages
  for all using (auth.uid() = user_id)
  with check (
    auth.uid() = user_id
    and exists (select 1 from public.threads t where t.id = thread_id and t.user_id = auth.uid())
  );
```

Apply it either by pasting it into the Supabase SQL Editor (the user runs this) or with `npx supabase db push` if the project is linked.

**Validate:** In the SQL Editor, run `select tablename, rowsecurity from pg_tables where schemaname = 'public';`. Both tables show `rowsecurity = true`. The two-user RLS check happens in Task C4.

## Phase B: Backend

### Task B1: Auth dependency

`auth.py` defines `get_current_user(authorization: str = Header(...))`:
- If the header is missing or isn't `Bearer <token>`, raise 401.
- `client = create_client(SUPABASE_URL, SUPABASE_ANON_KEY)`, then `user = client.auth.get_user(token).user`. If that fails, raise 401.
- `client.postgrest.auth(token)` so all table queries run as this user.
- Return a small dataclass with `user_id` and `db` (the client).

**Validate:** With the server running (`backend/venv/Scripts/python -m uvicorn app.main:app --reload --app-dir backend`), `curl -i localhost:8000/api/threads` returns 401, and `curl -i -H "Authorization: Bearer garbage" localhost:8000/api/threads` also returns 401.

### Task B2: Threads + messages endpoints

`routers/threads.py`. Every route depends on `get_current_user` and runs queries through `user.db`:

| Method | Path | Behaviour |
|--------|------|-----------|
| GET | `/api/threads` | List the user's threads, newest `updated_at` first |
| POST | `/api/threads` | Create a thread (title `New chat`, `openai_conversation_id` null) and return it |
| DELETE | `/api/threads/{id}` | Delete the thread (messages cascade); 404 if no row matched |
| GET | `/api/threads/{id}/messages` | Messages in ascending `created_at` order; 404 if the thread isn't visible |

Request and response bodies are Pydantic models in `models.py`.

**Validate:** Get a test user's access token. Either sign up in the frontend later, or run the curl below against `$SUPABASE_URL/auth/v1/token?grant_type=password` with the `apikey` header. Then:
- `curl -X POST -H "Authorization: Bearer $T" localhost:8000/api/threads` returns a thread JSON.
- `GET /api/threads` includes that thread.
- `GET /api/threads/<id>/messages` returns `[]`.
- `DELETE` returns 204, and a second `GET` no longer lists it.

### Task B3: LLM service with LangSmith tracing

`services/llm.py`:
- `client = wrap_openai(OpenAI(api_key=...))` from `langsmith.wrappers`. Tracing turns on when `LANGSMITH_TRACING=true` and `LANGSMITH_API_KEY` are set.
- `ensure_conversation(thread) -> str`: if `openai_conversation_id` is null, call `client.conversations.create()` and save the ID to the thread.
- `stream_reply(conversation_id, user_text)` is a generator. It calls
  ```python
  client.responses.create(
      model=settings.OPENAI_MODEL,
      conversation=conversation_id,
      input=user_text,
      instructions="You are a helpful assistant. Use file_search to answer from the user's documents when relevant. Say so when the documents don't contain the answer.",
      tools=[{"type": "file_search", "vector_store_ids": [settings.OPENAI_VECTOR_STORE_ID]}],
      stream=True,
  )
  ```
  and maps the stream events to small tuples:
  - `response.output_text.delta` → `("delta", {"text": event.delta})`
  - `response.file_search_call.in_progress` / `.searching` → `("tool", {"name": "file_search", "status": "searching"})`
  - `response.file_search_call.completed` → `("tool", {"name": "file_search", "status": "done"})`
  - `response.completed` → `("completed", {})`
  - `error` / `response.failed` → `("error", {"message": ...})`
- Decorate the function with `@traceable(name="chat_turn")` so the whole turn appears as one LangSmith run. If `wrap_openai` doesn't trace `responses.create` streaming in the installed `langsmith` version, check the langsmith docs and fall back to `@traceable` that records the input and the final text.

**Validate:** A throwaway script (`backend/venv/Scripts/python -c "..."`) creates a conversation, calls `stream_reply` with "What documents do you have access to?", and prints the deltas. Then:
- The script prints a coherent answer, and at least one `tool` event fires.
- A second call on the same conversation ("What did I just ask you?") answers correctly, which proves OpenAI is managing the memory.
- A `chat_turn` run shows up in the LangSmith project.

### Task B4: SSE chat endpoint

`routers/chat.py` has `POST /api/threads/{id}/messages` with body `{"content": str}` (Pydantic, `min_length=1`):
1. Load the thread through `user.db` (404 if not found), then `ensure_conversation`.
2. Insert the user message row. If the thread title is still `New chat`, set it to the first 50 characters of the message.
3. Return `StreamingResponse(gen(), media_type="text/event-stream", headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})`, where `gen()` yields `event: <type>\ndata: <json>\n\n` for each tuple from `stream_reply` and collects the delta text.
4. On `completed`, insert the assistant message row with the full text, bump `threads.updated_at`, then yield `event: done` with `{"message_id": ...}`.
5. On an exception, yield `event: error` and don't save a partial assistant message.

**Validate:**
- `curl -N -X POST -H "Authorization: Bearer $T" -H "Content-Type: application/json" -d '{"content":"hello"}' localhost:8000/api/threads/<id>/messages` shows `event: delta` lines arriving one by one, then `event: done`.
- `GET .../messages` then returns 2 rows (user and assistant).
- `tests/test_sse.py` monkeypatches `stream_reply` and the auth dependency, and asserts the response body contains the `delta` and `done` events in order. It passes with pytest.

**Checkpoint B:** The full chat loop works over curl, and the traces are visible in LangSmith.

### Task C2: API client + SSE parser

`lib/api.ts`:
- `apiFetch(path, init)` attaches `Authorization: Bearer <session.access_token>` and prefixes `VITE_API_URL`.
- Typed helpers: `listThreads`, `createThread`, `deleteThread` and `listMessages`.
- `streamMessage(threadId, content, handlers: {onDelta, onTool, onDone, onError}, signal)` POSTs with `fetch` and reads `res.body.getReader()` through a `TextDecoder`. It buffers until `\n\n`, parses the `event:` and `data:` lines, and dispatches to the handlers. It must handle a chunk that ends partway through an event.

**Validate:** `npm run build` passes (type check). The end-to-end check in C3 confirms the streaming.

### Task C3: Chat UI

- `pages/Chat.tsx` is a two-column layout: `ThreadSidebar` on the left (fixed width; collapsible below `md`) and the conversation on the right.
- `ThreadSidebar` has a "New chat" button, a thread list (title, active highlight), a delete button on hover and a sign-out button at the bottom.
- `MessageList` shows user and assistant bubbles, auto-scrolls to the bottom while streaming, and renders a muted "Searching documents…" line while a `tool` event is in the `searching` state.
- `MessageInput`: a textarea where Enter sends and Shift+Enter adds a newline. It's disabled while streaming.
- Flow: if no thread is selected, the first send creates one. Add the user message optimistically, append deltas to an assistant placeholder, and on `done` refresh the thread list (to pick up the new title and order). On `error`, show the error under the message.

**Validate (browser):**

- Ask a follow-up ("summarise what you just said") and get an answer that uses the earlier turn.
- Reload the page, open the thread, and the full history is shown.
- The sidebar title changes from "New chat" to the first message.
- Deleting the thread removes it from the list.

## Risks / Notes

- **Responses API event names and the `conversation` parameter** depend on the version of the `openai` SDK. Check against the installed SDK, using `help(client.responses.create)`, before writing the mapper in B3.
- **SSE buffering:** if deltas arrive all at once, look for proxy or compression middleware buffering the response. Don't add GZip middleware.
- **Windows:** the venv binaries are under `venv/Scripts/`, not `venv/bin/`.
- **Module 2 note:** the plan for Option A (replace) removes `openai_conversation_id`, `ensure_conversation` and the `file_search` tool, and keeps the `threads` and `messages` tables.
