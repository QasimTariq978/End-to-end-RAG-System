# Plan 4: Retrieval Tool in Chat (Module 2, part 2 of 2)

⚠️ **Medium**: Single-pass is realistic. The hard part is streaming tool calls: tool-call fragments arrive as deltas across chunks and have to be stitched together. `openrouter/free` also routes each request to a different free model, so tool-calling quality varies between turns. **It depends on plan 3** (`chunks` must hold embedded rows).

## Goal

When the user asks about their documents, the model calls a `search_documents` tool. The backend embeds the query, runs a vector search over **only that user's** chunks (RLS), and returns the best matches above a relevance threshold. The model then answers from them and cites the filenames. The UI shows "Searching documents for "…"" while the search runs, and lists the sources under the answer. General questions are answered without a search.

## Out of Scope

- Hybrid or keyword search and reranking (Module 6)
- Metadata filters (Module 4)
- Saving tool calls or sources to the database. History stays as user/assistant text only, and the sources line disappears on reload. A later module can add a `sources` column.
- Other tools (Module 7) and sub-agents (Module 8)

## Prerequisites

- Plan 3 is complete, and at least one `ready` document exists for the test user.
- OpenRouter credit is in place (query embeddings use the same paid model).

## Key Decisions

1. **The search runs in a SQL function**, `public.match_chunks(query_embedding, match_count, min_similarity)`. It is `security invoker`, so RLS on `chunks` and `documents` limits results to the caller. The backend calls it with `user.db.rpc(...)`. Using the service-role key was rejected for this.
2. **Similarity is cosine** (`1 - (embedding <=> query)`) and uses the HNSW `vector_cosine_ops` index from plan 3.
3. **The threshold and top-k come from env:** `RETRIEVAL_TOP_K=5` and `RETRIEVAL_MIN_SIMILARITY=0.3`. text-embedding-3-small scores relevant passages at roughly 0.3–0.7. Task B5 checks the threshold against real data and adjusts the default if needed.
4. **The tool loop lives in `llm.stream_reply`.** The loop:
   - stream a completion with `tools=[SEARCH_TOOL]`
   - collect `delta.tool_calls` fragments by `index`
   - when `finish_reason == "tool_calls"`, run each tool, append the assistant `tool_calls` message and one `role: "tool"` message per call, then stream again
   - stop after `MAX_TOOL_ROUNDS = 3`. The last round is sent **without** `tools`, which forces a text answer.
5. **`llm.py` never touches the database.** `stream_reply(messages, execute_tool)` receives a callback. `chat.py` builds it as a closure over `user.db`, so all RLS stays in the router layer.
6. **Tool arguments are parsed with Pydantic** (`SearchDocumentsArgs(query: str = Field(min_length=1))`). Invalid JSON or a missing query isn't an exception. It goes back to the model as the tool result, `"Invalid arguments: …"`, so the model can retry.
7. **Tool result format** for the model: numbered blocks `[1] <filename> (chunk <n>, similarity 0.62)\n<content>`. With no hits above the threshold the result is `"No relevant passages found in the user's documents."`
8. **SSE contract** (adds fields; nothing that exists changes):
   - `event: tool` `{"name": "search_documents", "status": "searching", "query": "…"}`
   - then `event: tool` `{"name": "search_documents", "status": "done", "sources": [{"document_id", "filename"}]}` (unique per document, in rank order)
9. **System prompt:**
   - The model has a `search_documents` tool over the user's uploaded files and should use it for any question that might be answered by them.
   - It answers only from the returned passages and cites filenames in square brackets, like `[handbook.md]`.
   - If the search finds nothing relevant, it says so plainly and doesn't guess.
   - It answers general-knowledge chit-chat without searching.
10. **LangSmith:** `search_documents` is `@traceable(run_type="retriever")` and returns the documents in LangSmith's retriever format, so each chat turn's trace shows `chat_turn → completion → retriever → completion`.

## Phase A: Database

### Task A1: Migration `004_match_chunks.sql`

```sql
create or replace function public.match_chunks(
  query_embedding extensions.vector(1536),
  match_count int default 5,
  min_similarity float default 0.3
)
returns table (
  id uuid,
  document_id uuid,
  filename text,
  chunk_index int,
  content text,
  similarity float
)
language sql stable
security invoker
set search_path = public, extensions
as $$
  select c.id, c.document_id, d.filename, c.chunk_index, c.content,
         1 - (c.embedding <=> query_embedding) as similarity
  from public.chunks c
  join public.documents d on d.id = c.document_id
  where d.status = 'ready'
    and 1 - (c.embedding <=> query_embedding) >= min_similarity
  order by c.embedding <=> query_embedding
  limit match_count;
$$;

revoke execute on function public.match_chunks from public, anon;
grant execute on function public.match_chunks to authenticated;
```

**Validate:** in psycopg, impersonating a user (`set local role authenticated; set local request.jwt.claims = '{"sub":"<user A id>"}'`), call the function with the stored embedding of one of A's chunks. That chunk comes back first with similarity ≈ 1.0. The same call as user B returns 0 rows.

### Task B3: Tool loop in `llm.py`

```python
SEARCH_TOOL = {"type": "function", "function": {
    "name": "search_documents",
    "description": "Search the user's uploaded documents for passages relevant to a query.",
    "parameters": SearchDocumentsArgs.model_json_schema(),
}}
MAX_TOOL_ROUNDS = 3

ToolExecutor = Callable[[str, str], tuple[str, dict]]
# (name, raw_json_args) -> (result_text_for_model, done_event_payload)

@traceable(name="chat_turn", reduce_fn=_reduce_outputs)
def stream_reply(messages, execute_tool: ToolExecutor | None = None) -> Iterator[StreamEvent]:
```

Algorithm:
1. Set `convo = list(messages)`.
2. For each `round` in `range(MAX_TOOL_ROUNDS + 1)`:
   - Send `tools=[SEARCH_TOOL]` only if `execute_tool` is given and `round < MAX_TOOL_ROUNDS`.
   - Stream a completion. For each chunk:
     - Handle the `error` field exactly as now.
     - Yield `("delta", …)` for content.
     - For each `delta.tool_calls` item, accumulate into `calls[tc.index]`. Set `id` and `function.name` when present, and concatenate `function.arguments`.
     - Record `finish_reason`.
   - If `calls` is non-empty, which covers some models that send tool calls with `finish_reason="stop"`:
     - Append `{"role": "assistant", "content": <text so far or None>, "tool_calls": [...]}` to `convo`.
     - For each call, parse the arguments for the event. On a parse failure, `query = None`.
     - Yield `("tool", {"name", "status": "searching", "query"})`.
     - Call `result, done = execute_tool(name, args_json)`.
     - Yield `("tool", {"name", "status": "done", **done})`.
     - Append `{"role": "tool", "tool_call_id": id, "content": result}`.
     - `continue` to the next round.
   - Otherwise, yield `("completed", {})` and `return`.
3. The SSE `delta` text from every round is joined into the saved assistant message, which is what `chat.py` already does.

`chat.py` builds the executor:

```python
def execute_tool(name: str, raw_args: str) -> tuple[str, dict]:
    if name != "search_documents":
        return f"Unknown tool: {name}", {"sources": []}
    try:
        args = SearchDocumentsArgs.model_validate_json(raw_args or "{}")
    except ValidationError as exc:
        return f"Invalid arguments: {exc.errors()[0]['msg']}", {"sources": []}
    rows = retrieval.search_documents(user.db, args.query)
    return retrieval.format_results(rows), {"sources": retrieval.unique_sources(rows)}
```

Pass it as `llm.stream_reply(messages, execute_tool)`. Update `SYSTEM_PROMPT` as in Key Decision 9.

## Risks / Notes

- **Free-model variance:** `openrouter/free` picks a different model per request. Some models ignore tools, call them with bad JSON, or narrate instead of calling. The Pydantic error path and the round cap handle bad calls. If quality is too erratic, pin `OPENROUTER_MODEL` to a specific free model with tool support and record which one here.
- **Streamed tool-call shape:** some providers send the whole tool call in one chunk, others split it. Some omit `id` on later fragments. Key everything by `index`. If a provider sends no `id`, generate `call_<round>_<index>`.
- **`finish_reason` quirks:** the loop runs whenever tool calls were gathered, whatever `finish_reason` says.
- **Threshold:** 0.3 is a starting point. Record the scores observed in B5 here.
- **History:** tool messages aren't saved, so on a later turn the model doesn't see earlier passages and searches again. That costs one embedding call per search and keeps the history small.
